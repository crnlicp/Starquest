Build a web app called "Star Quest" — a fun family behavior tracker where parents give children points for good behavior and take points away for bad behavior. Kids collect points, level up, and spend them on rewards. The app must feel like a game: colorful, playful, and full of animation, and simple enough for a 5-year-old to use without help. It is deployed on the Internet Computer (ICP).

## TECH STACK
- Tooling: `icp` CLI (`icp.yaml`) for local network, build and deploy; `mops` (`mops.toml`) for the Motoko toolchain and packages.
- Frontend: React + TypeScript (Vite), served from a frontend canister using the `@dfinity/static-site` recipe (certified assets; SPA routing via `_redirects`, headers/CSP via `_headers`).
- Backend: Motoko canister (`@dfinity/motoko` recipe, `mo:core` standard library, enhanced orthogonal persistence).
- Auth: Internet Identity via `@icp-sdk/auth` (`AuthClient`, mainnet II at `https://id.ai` by default); backend calls via `@icp-sdk/core` with TypeScript bindings generated by `@icp-sdk/bindgen` from the committed `.did` file.
- Canister IDs and the root key reach the frontend through the `ic_env` cookie (`safeGetCanisterEnv()`); no `.env` files with canister IDs, and never fetch the root key at runtime.
- Animations: Framer Motion for UI motion, canvas-confetti for celebrations, Lottie for character/avatar animations.
- Charts: a lightweight React chart library (e.g., Recharts).
- Install as a PWA (add to home screen) so it feels native on iPhone and iPad.

## LOGIN & ACCESS
1. Parent (admin)
   - Logs in with Internet Identity (passkey or Google sign-in). No passwords.
   - The parent's principal owns the family. Only parents can create, edit, or delete child profiles.
   - Can invite a second parent/caregiver: share an invite link; the caregiver logs in with their own Internet Identity and joins the family as a parent.
   - Parents can remove a caregiver at any time.
2. Child
   - Children never sign up and never use Internet Identity, email, or passwords.
   - Kids can view, celebrate, and request rewards, but can NOT add or remove points.

## HOW KIDS ENTER THE APP
Option A: Shared/parent device (Kid Mode)
- Parent opens "Kid Mode" from their logged-in device.
- A playful screen shows all children's avatars; the child taps their own avatar.
- Leaving Kid Mode or opening parent settings requires a 4-digit parent PIN (set at first login, stored hashed, never in plain text).

Option B: Child's own device (pairing)
- From the child's profile, the parent taps "Connect a device", which shows a QR code and a 6-digit code (valid 10 minutes, single use).
- On the child's device, the kid taps "I'm a kid!" and scans the QR or types the code.
- The device generates its own anonymous key (Ed25519 identity) saved in the browser. The backend links that device principal to the child's profile with view-and-request permission only.
- That device then always opens straight into that child's Kid Mode.
- Parents can see all paired devices (name, child, last active) and disconnect any of them, which immediately revokes access.
- Limit wrong code attempts (e.g., 5 tries, then wait 1 minute).

Optional picture password
- Parents can turn on a simple picture password per child: tap 3 animal icons in the right order.
- Wrong attempts show a gentle shake, never an error message. Parent can reset it anytime.

## CORE FEATURES

### 1. Family & Child Profiles
- Parent adds multiple children: name, age, avatar, favorite color.
- Each child has a fun avatar character (animals/monsters/robots) chosen from a picker, which can be customized with unlocked items (hats, glasses, backgrounds).

### 2. Behaviors (Good & Bad)
- Parents create a list of behaviors, each with:
  - Name, emoji/icon, point value, type (Good ✅ or Oops ⚠️)
  - Optional: assign to specific children only
- Include a starter library of common behaviors parents can enable with one tap:
  - Good: Brushed teeth (+5), Made bed (+5), Helped a sibling (+10), Finished homework (+10), Ate vegetables (+5), Was kind (+10), Went to bed on time (+5), Cleaned up toys (+5)
  - Oops: Hitting (-10), Shouting (-5), Not listening (-5), Lying (-10), Screen time overuse (-5)
- Logging a behavior: parent picks child → taps behavior → done (2 taps max).
- Optional short note on each entry (e.g., "Shared toy with friend at park").
- Parents can backdate an entry and undo/delete mistakes.
- Custom one-off points: give any +/- amount with a reason.
- Points given by a parent appear on the child's paired device with the full animation.

### 3. Points, Levels & Progress
- Each child has a points balance (spendable) and total XP (lifetime, never decreases).
- Levels based on XP (e.g., Level 1 "Little Star" → Level 10 "Superstar Legend"), each with a title and badge.
- Daily goal: a progress ring that fills as the child earns points that day.
- Streaks: consecutive days meeting the daily goal, shown with a flame icon.
- Negative points reduce balance but never XP, and balance cannot go below zero.

### 4. Rewards Shop
- Parents create rewards with name, emoji/image, and point cost (e.g., Ice cream 30, Extra 30 min screen time 50, Trip to the playground 100, Movie night 150).
- Kids browse the shop as a treasure store and tap "I want this!" to send a request.
- Parent sees it in the approvals inbox, then approves or declines; on approval points are deducted with a celebration animation on the child's screen.
- "Saving for" goal: child can pin one reward and see a progress bar toward it.

### 5. Achievements & Badges
- Auto-unlock badges: First Star, 7-Day Streak, 100 Points Club, Kindness Hero (10x "Was kind"), Clean Room Champion, Comeback Kid (good day after an oops day), etc.
- Badges appear in a trophy shelf on the child's profile.
- Printable/shareable certificate when reaching a new level or big badge.

### 6. Recovery Missions (positive approach to bad behavior)
- After an "Oops", the app can suggest a "Make It Right" mission (e.g., say sorry, help clean up) that earns back some points when the parent confirms it.
- Tone for bad behavior is always gentle and encouraging — never shaming. Use words like "Oops!" and "You can do it next time!"

### 7. Reports for Parents
- Per-child dashboard: today, this week, this month, this year.
- Charts: points over time, good vs. oops ratio, most frequent behaviors.
- Activity history list with filters (child, type, date).
- Weekly summary card: "This week Emma earned 120 points and her top behavior was 'Helped a sibling'."
- Option to reset points (with confirmation) without losing history.

### 8. Settings
- Languages: English and Swedish (switchable, using an i18n setup), easy to add more.
- Sound effects on/off, animation intensity (full / reduced for motion sensitivity).
- Option to show/hide sibling leaderboard (off by default, to avoid unhealthy competition).
- Daily in-app reminder for parents to log behaviors.
- Change parent PIN, manage caregivers.
- Manage paired devices and picture passwords per child.

## GAMIFIED UI & ANIMATIONS (very important)
- Overall style: bright, rounded, cartoon-like; big chunky buttons; soft shadows; playful fonts; lots of emoji and icons.
- Earning points: stars/coins fly from the button into the child's point counter, the counter rolls up, the avatar jumps/cheers, with a happy sound.
- Oops: gentle wobble of the avatar, a small sad-but-cute face, points float down softly. No harsh colors or loud sounds.
- Level up: full-screen celebration with confetti, fireworks, the new badge spinning in, and the avatar dancing.
- Badge unlock: treasure chest opens with sparkles and reveals the badge.
- Reward approved: gift box shake + pop animation with confetti.
- Streaks: animated flame that grows bigger with longer streaks.
- Daily goal ring fills with a smooth animation and bursts with stars when completed.
- Device pairing success: the child's avatar "teleports" onto the new device with a sparkle burst.
- Home screen: avatars of each child bounce gently; idle animations (blinking, waving) make the app feel alive.
- Micro-interactions everywhere: buttons squish when tapped, cards slide and bounce in, smooth page transitions.
- Respect the "prefers-reduced-motion" setting and the in-app animation setting.

## KID-FRIENDLY DESIGN
- Kid Mode uses icons and pictures first, minimal text, very large touch targets.
- Optional "read aloud" button that speaks text for kids who can't read yet (browser Web Speech API).
- Each child's screen uses their favorite color as the theme.
- No ads, no external links, and nothing confusing or scary in Kid Mode.
- Mobile-first and responsive: works great on phones, tablets, and desktop.

## BACKEND (MOTOKO) REQUIREMENTS
- Single Motoko actor (persistent by default on moc 2 — enhanced orthogonal persistence) so all data survives canister upgrades. Never lose family data on deploy.
  - No `stable` keyword, no `preupgrade`/`postupgrade`, no `mo:base`.
  - Stable fields have no inline initializers; their initial values come from the mops-managed migration chain in `canisters/backend/src/migrations/` (from the very first version). Non-stable-compatible changes go in the single pending migration; applied migrations are never edited.
  - Code layout (`canisters/backend/src/`): `types.mo` (types), `lib/` (stateless domain logic), `mixins/` (public API, state passed in as parameters), `main.mo` (composition root, owns state, no public methods), `backend.did` (committed).
- Data model: Family, Parent (principal), Child, PairedDevice (principal → childId), Behavior, LogEntry, Reward, RewardRequest, Badge, PairingCode, Settings.
- Access control on every public function using msg.caller:
  - Reject anonymous callers.
  - Parents can only access their own family.
  - Paired device principals can only read their own child's data and create reward requests.
- Use query functions for reads and update functions for writes.
- Validate all inputs (name lengths, point ranges, balance never below zero).
- Store the parent PIN and picture passwords as hashes.
- Pairing codes: random, single use, expire after 10 minutes, rate-limited.
- Provide a "getChangesSince(timestamp)" query so child devices can poll efficiently.

## ICP DEVELOPMENT NOTES
- Set up with the `icp` CLI using path-based canisters: `icp.yaml` lists `canisters/*`; `canisters/backend/` (Motoko, own `canister.yaml` + `mops.toml`) and `canisters/frontend/` (React Router + Vite, own `canister.yaml` + `package.json`, build output `build/client`). The root holds only `icp.yaml`, a scripts-only `package.json`, `scripts/` and `docs/`.
- Generate the Candid interface with `mops generate candid backend`, commit the `.did`, and generate TypeScript bindings into `app/bindings/` with `@icp-sdk/bindgen` at build time (bindings are not committed).
- Local development: `icp network start -d` then `icp deploy --identity anonymous` (the local network is per project). Sign-in uses mainnet II even locally; a local II (`ii: true`) is only for offline work.
- Commit `.icp/data/` (holds mainnet canister IDs); ignore `.icp/cache/`.
- Use optimistic UI: play point/level-up animations instantly on tap, then confirm with the backend in the background, and roll back gently if a call fails.
- For "live" updates on child devices, poll getChangesSince every few seconds while the app is open; refresh immediately when the app regains focus.
- Keep everything on-chain: no external servers or third-party APIs. Bundle all sounds, avatars, and animations with the frontend.
- Keep images small (compress avatar photos and reward images) to save storage and cycles.
- Use in-app notifications (badge counts, approvals inbox) instead of push notifications.
- Must work on the local network and when deployed to ICP mainnet (`icp deploy -e ic` with `prod-identity`, never the anonymous one; every mainnet action needs explicit approval).
- Decide the app's final origin (canister URL or custom domain) before real families sign up: Internet Identity principals are tied to the origin they were created under.

Make the first version fully working end-to-end with the starter behaviors and a few sample rewards preloaded, so a new family can start using it within one minute.
